# Pie mate 토큰 효율 설계 — 심사 기준별 증명

## 1. 사용자 요구사항 및 워크플로
- **대상 사용자**: 친구·모임·여행에서 함께 쓴 돈을 나누는 사람들. 문제: 조건이 섞인 정산(덜 내기·퍼센트·한도)을 손으로 계산하다 틀리고, 누가 냈는지 증명하기 어렵다.
- **워크플로 (입력 → 결과물)** — 단계 이름은 사용량 기록(`usage.jsonl`)의 `stage`와 같아요.

| 단계 | 하는 일 | 누가 | 토큰 |
|---|---|---|---|
| chat.route / group.pie | 요청 종류 판단 (나누기·추천·사용법·잡담) | **코드 규칙** | 0 |
| settlement.analyze (Stage 1) | 말로 한 조건 → 구조화된 규칙 | **AI** (단순 나누기는 E2 코드) | 조건 있을 때만 |
| settlement.calculate (Stage 2) | 1원 단위 분담 · 합계 검증 · 지출 한도 | **코드** | 0 |
| settlement.explain (Stage 3) | 결과 설명 | **AI** (똑같이 나누기는 E3 문장 틀) | 조정 있을 때만 |
| assistant.step | 추천·대화 — 도구(메뉴·상품·여행 검색, 조합 검증) 선택 | **AI** + 코드 검증 | 필요한 도구 설명만 (E1) |
| 온체인 | 정산 등록·예치·지급·중단 (Sepolia) | **코드 + 컨트랙트** | 0 |
| 증거·분쟁 | 인증서·기록으로 제3자 검토, 이의제기 판정 | AI 판정 + 코드 기록 | 이의제기 때만 |

## 2. Kiln API 통합 및 효율성
- **모델**: `KILN_MODEL=qwen3-32b` (심사 기준 · NPU 기반 Kiln API). 요청마다 **`/no_think`로 긴 사고를 꺼서** 불필요한 추론 토큰을 줄이고, 어려운 판단이 필요한 분쟁 판정(`dispute.investigate`)·구매 계획(`shopping.plan`)만 사고를 허용해요 (`agent/llm.py` THINK_STAGES). 벤치 보고서 첫 줄에 Kiln 모델 목록에 이 모델이 실제로 있는지 기록돼요.
- **API 응답 → 결정**: 모든 Kiln 호출 뒤에 결정 기록이 남아요 (`llm.decision`, 사용량 기록 `mode=decision`).
  예: `Kiln 응답 → 도구 호출: menu_price_search` · `Kiln 응답 → 분담 규칙 JSON: …` · `코드 가드: 근거 없는 금액 → 되묻기` · `코드 가드: 검증 안 된 조합 → check_delivery_combos 강제`.
- **단계별 토큰 보고**: 앱의 'AI 사용량' 화면(단계별) · `usage.jsonl`(호출마다 stage·입력/출력 토큰·지연·에너지) · `tests/token_bench.py` 보고서(단계별 기준선 vs 효율).

### 불필요한 추론을 줄이는 설계
| # | 설계 | 단계 | 효과 |
|---|---|---|---|
| — | 금액 계산·합계 검증·지출 통제·온체인은 처음부터 코드 | calculate 등 | AI가 숫자를 추론하지 않음 (정확도 + 0 토큰) |
| E1 | 요청 종류별로 필요한 도구 설명만 (음식 → 메뉴 검색·조합 / 여행 → 여행 검색 / 사용법 → 도구 없음) | assistant.step | 도구 설명 3,584자 → 1,526자 (음식, −57%) |
| E2 | 금액·인원만 있는 단순 나누기 → 코드 해석 | settlement.analyze | AI 호출 0회 |
| E3 | 똑같이 나눈 결과 → 문장 틀 설명 | settlement.explain | AI 호출 0회 |
| E4 | 그룹방 '파이야'만 → 코드 안내 | group.pie | AI 호출 0회 |
| E5 | 예시 3→2개 · 지식은 사용법·상태 질문일 때만 2조각 | 프롬프트 | 입력 토큰 ↓ |
| E6 | 대화 기록 8→6개 · 400→300자 | 프롬프트 | 입력 토큰 ↓ |
| E7 | qwen3-32b · `/no_think` (분쟁 판정·구매 계획만 사고 허용) | 모든 AI 호출 | 추론(출력) 토큰 ↓ |

모든 효율 설계는 `.env`의 `PIE_EFFICIENT=0`으로 끌 수 있어서, 같은 입력으로 기준선과 비교할 수 있어요.

### 에너지 추정 가정
- 호출마다 **실제로 잰 Kiln 응답 시간(초) × `NPU_POWER_WATTS` × `NPU_COUNT` ÷ 3600 = Wh** (`agent/usage.py`).
- NPU가 그 시간 동안 이 요청만 처리했다고 보는 **상한값** — 실제 서버는 여러 요청을 묶어 처리하므로 더 작아요.
- `NPU_POWER_WATTS`·`NPU_COUNT`는 Kiln이 쓰는 NPU 보드 사양에 맞춰 `.env`에 넣어요 (기본 150 W × 1). 코드로 처리한 단계는 0 Wh.
